# ADHD 友好的微步陪学讲解设计

## 目标

将题目页从“默认读者能补全推理”的技术说明，改为适合零基础、理解节奏慢且易被长句分散注意力的陪学材料。内容仍须准确、完整，并保留每个来源方案、代码与可视化。

## 非目标

- 不删除任何官方或社区方案。
- 不降低算法正确性要求，不把真实 trace 改成演示数据。
- 不新增引擎组件或改变播放器数据契约。

## 教学结构

页面保持既有顺序：原题 → 题目拆解与通用切入点 → 官方解法 → 社区高赞解法 → 复杂度对比。

每个章节改用“微步陪学”单元。一个单元只引入一个新的判断、概念或操作，并依次包含：

1. **眼前目标**：先说这一小步要解决的具体问题。
2. **人话概念**：先用日常语言说明，首次再在括号中给术语，例如“把以前算过的答案记下来（记忆化）”。
3. **极小例子**：用两个到六个元素的例子手工走一遍；先显示已知信息，后引出规则。
4. **可跳过的五秒判断**：仅在信息足够时问一个局部判断；紧跟答案，不把思考失败当作继续阅读的障碍。
5. **落地与记忆句**：说明这一步在算法或可视化中的位置，并用一句话写出此刻唯一要记住的事。

## 文案规则

- 每个段落只承担一个概念；优先两到四句的短段。
- 先陈述事实、再陈述原因；避免多层嵌套因果和未解释的抽象名词。
- 新术语必须先有日常说法和当下用途，不能只给定义。
- 公式出现前，先用具体数值例子展示它在算什么；公式后立刻翻译成自然语言。
- 每个方案必须先说“它在解决上一方案的哪个困难”，再给步骤或代码。
- 明确边界：例如 `tails` 是“各长度的最小结尾记录”，**不是**最终的 LIS；`dp[i]` 是“以 i 结尾”的答案，**不是**整个数组的答案。
- `:::insight` 只放一个可复述的关键判断；`:::pitfall` 只放一个真实易错点。

## 可视化与互动

播放器仍由真实 trace 驱动。帧说明采用固定顺序：当前动作 → 原因 → 当前结果，且每句尽量短。

“五秒判断”以普通文字小节呈现，带“直接看答案”句子，不引入需要额外 Markdown 或播放器交互的新组件。问题只能要求读者判断当前一格、一个指针或一个选择，不能要求在脑中重做完整算法。

## Skill 与验收

`leetcode-explanation-generator` 必须将上述结构写入生成流程和评分量表。每次生成或修订均须检查：

- 是否默认读者具备未解释的先验知识；
- 是否存在超过一个新概念的段落或结论先行；
- 每个思考提示前是否已提供足够信息、后是否立即解释；
- 每个方案结尾是否有明确的“现在只记住什么”；
- 所有来源方案、真实 trace、代码和独立播放器是否仍完整保留。

## 验证

更新 LC 80 与 LC 300 的“题目拆解”和全部方案讲解后，运行 trace `--check`、索引构建、自动化测试、浏览器控制台与独立播放器交互检查。页面评审以短句、概念首次解释、可跳过思考提示和记忆句为重点，而不以单纯缩短总字数为目标。
