# LeetCode Explanation Generator

Create a teaching package that makes the learner's precise blockage the organizing constraint, rather than producing a generic solution write-up.

## Required inputs

Collect all of the following before writing artifacts:

1. A LeetCode link or full problem description.
2. A specific learner confusion, not only “this is hard”.
3. An optional attempted idea, including a wrong or incomplete one.

If only a link is supplied, read the official problem page. If a material rule remains ambiguous, ask for clarification rather than inventing it.

## Contract-first workflow

1. Read the target project's `docs/ENGINE-SPEC.md`; follow its current trace schema and Markdown safe subset exactly.
2. Read `engine/viz-registry.js` before selecting a visualization.
3. Classify the algorithmic pattern (for example, pointers, stack, traversal, DP, backtracking, or greedy state scan).
4. Reuse a registered `vizType` whenever it can teach the operation clearly. A scalar state such as cumulative profit may live in a frame note when the highlighted positions make the state transition visible. Do not add or alter an engine component merely to improve appearance.
5. If no registered component fits, first prototype the explanation with `description` and `note` fields. Only report a proposed new component when that representation remains inadequate; do not implement it without an explicit design decision.

## Build the package

Create the problem directory and its normal page files. The minimum teaching artifacts are:

- `generate_trace.py`: executes the real optimal algorithm and writes `trace.json`; implement `--check` to validate the produced trace.
- `trace.json`: generated by the script, never hand-authored frames.
- `meta.json`: uses a registered `vizType` and contains Python/C++ code equivalent to the generator algorithm.
- `explain.md`: uses the eight sections below and only the Markdown subset permitted by the engine.

Use a small non-trivial input that exposes the key branch. Frame every learner-relevant decision: the active position(s), the action, and why that action is safe. Prefer a compact sequence of meaningful frames over one frame per incidental assignment.

## Eight-section explanation contract

Write concise paragraphs that remain comfortable in a 780px reading column. Include every section, in this order.

### 0. 问题重述

Restate input, output, and hidden constraints in plain language. Do not copy the problem statement.

### 1. 暴力解法推导

This is mandatory and must be a narrative, not a result label. Begin from a no-idea starting point: what would someone naturally try first, where would that approach get stuck, and what next experiment forms the brute-force algorithm. Name the likely blockage and directly address the supplied learner confusion.

### 2. 暴力解法的代价

Use a concrete input to show the work done (moves, candidate pairs, or branches), then give the complexity intuition. Do not rely on an abstract Big-O statement alone.

### 3. 优化的关键洞察

Show which repeated work or discarded information in the brute approach triggers the observation. Explain why that observation licenses the optimization; do not write only “we find that …”.

### 4. 最优解法讲解

Walk through the chosen visual trace. Tie the invariant, pointer/state changes, and each key branch to the frame notes.

### 5. 代码实现

Include Python and C++ implementations equivalent to the verified generator algorithm. Comment only the decisions that carry the invariant.

### 6. 复杂度总结与变体

State time and space complexity and one concise, relevant variation or follow-up.

### 7. 自检清单

Include a visible checklist confirming brute-force derivation, direct response to the confusion, generated-and-checked trace, visual review, code consistency, and Markdown safety.

## Verification gate

Run these before declaring success:

1. `python3 generate_trace.py` and `python3 generate_trace.py --check`.
2. The repository index build and automated tests.
3. Execute both displayed implementations on the trace input and compare the result with the generator.
4. Open the actual page in a browser. Check console output, initial state, meaningful frame transitions, slider/buttons/playback, Markdown, and code-language switching. When two named pointers can share a cell, also check that both labels are visible rather than clipped or overlapped.
5. Audit the explanation against [the teaching rubric](references/teaching-rubric.md). Revise it if section 1 is merely a conclusion, if section 3 lacks a causal bridge from brute force, or if the visualization hides the core decision.

## Report the design decision

For test runs and new patterns, report: the learner confusion, the evidence that the brute-force derivation addresses it, the visualization choice and rejected alternatives, browser result, and remaining design concern. Treat a questionable visual fit as a design finding—not permission to expand the engine.
