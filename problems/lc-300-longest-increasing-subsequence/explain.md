## 原题

### 300. Longest Increasing Subsequence

Given an integer array `nums`, return the length of the longest strictly increasing subsequence.

### Example 1

Input: `nums = [10,9,2,5,3,7,101,18]`

Output: `4`

Explanation: The longest increasing subsequence is `[2,3,7,101]`, therefore the length is `4`.

### Example 2

Input: `nums = [0,1,0,3,2,3]`

Output: `4`

### Example 3

Input: `nums = [7,7,7,7,7,7,7]`

Output: `1`

### Constraints

- `1 <= nums.length <= 2500`
- `-10^4 <= nums[i] <= 10^4`

Follow up: Can you come up with an algorithm that runs in `O(n log(n))` time complexity?

## 题目拆解与通用切入点

这题的判题契约是只返回**长度**，不要求返回那条子序列；“subsequence” 表示可以跳过元素，但保留的相对顺序不能变；“strictly increasing” 要求后一个数严格大于前一个数。`n` 最多为 `2500`，所以 `O(n^2)` 可以作为第一套可靠方案，但 Follow up 明确提示还要理解 `O(n log n)` 的优化。

你说自己“一点思路都没有”，这很正常：难点不是循环，而是“前面这么多数字，哪些历史信息需要保留”。这是典型的**相邻有关的序列问题**：当前数能否接上，取决于它和某个前项的大小关系。通用切入点是固定“最后一个选中的位置”，问“如果答案以 `nums[i]` 结尾，它最好能有多长？”这样把全局选法拆成很多个只关心一个结尾位置的小问题。

接着检查不同历史能否压缩：同长度的两个候选若结尾分别是 `10` 与 `2`，更小的 `2` 对未来更友好——任何能接在 `10` 后的数也能接在 `2` 后。这种“同长度只保留最优代表”的观察，是从 DP 走向贪心 + 二分的通用入口。

:::insight
先不要直接找整条最长序列。先改写成“每个位置结尾时的最好答案”，再问状态中有没有被更优代表支配的历史信息；这是序列 DP 与状态压缩题常用的两步切入法。
:::

## 官方解法

### 方案一：动态规划

令 `dp[i]` 表示**以 `nums[i]` 结尾**的最长严格递增子序列长度。每个数自己都能组成长度 `1` 的序列，所以 `dp` 先全设为 `1`。为了计算 `dp[i]`，枚举每个 `j < i`：只有 `nums[j] < nums[i]` 时，才能把 `nums[i]` 接在以 `nums[j]` 结尾的序列之后，候选长度就是 `dp[j] + 1`，取最大值。

关键是固定“最后一个数”。例如 `7` 前面既可以有 `[2,5]`，也可以有 `[2,3]`；之后能否接 `101` 时，只需要“在 `7` 结束的最长长度”，不必保存每一条完整路径。

:::viz approach="official-dp"
:::

最终答案是所有 `dp[i]` 的最大值。时间复杂度 `O(n^2)`，空间复杂度 `O(n)`。

### 方案二：构建候选序列（线性扫描）

官方第二种方法构建候选数组 `sub`：第 `k` 位保存“长度为 `k + 1` 的递增候选中，当前最小的结尾”。处理 `num` 时，若它大于 `sub` 的最后一个数，就能延长长度；否则从左到右找到第一个 `>= num` 的位置并替换。

为什么替换安全？对 `[8,1,6,2,3,10]`，得到 `[1,6]` 后遇到 `2`，把 `6` 改成 `2` 得到 `[1,2]`，不损失长度 `2` 的可能性，却给未来更多接续机会；随后 `3` 才能把长度扩成 `3`。

:::viz approach="official-greedy-linear-scan"
:::

每次最坏要线性扫描 `sub`，时间复杂度仍为 `O(n^2)`，空间复杂度 `O(n)`。

:::pitfall
`sub` 只保存各长度最小的结尾，不一定是原数组中的真实子序列。例如 `[3,4,5,1]` 最终可能显示为 `[1,4,5]`；它不是原数组的子序列，但长度仍正确。
:::

### 方案三：构建候选序列（二分查找）

上个方案真正耗时的是找第一个 `>= num` 的位置。`sub` 始终递增，所以可用 `lower_bound` / `bisect_left` 二分定位，而追加或替换的规则完全不变。每个数从 `O(n)` 降到 `O(log n)`，总时间变为 `O(n log n)`，空间仍为 `O(n)`。

:::viz approach="official-greedy-binary-search"
:::

## 社区高赞解法

### 方案一：记忆化搜索

社区先用递归表达状态：`dfs(i)` 表示以 `nums[i]` 结尾的 LIS 长度。它枚举 `j < i`，只要 `nums[j] < nums[i]` 就尝试 `dfs(j) + 1`；没有可接前项时结果就是 `1`。多个调用会需要同一个 `dfs(i)`，所以缓存结果，每个下标只真正计算一次。播放器中的空格代表尚未算出的状态，亮格是刚写入缓存的状态。

:::viz approach="community-memoized-dfs"
:::

状态数是 `n` 个，每个状态枚举此前位置，时间 `O(n^2)`；缓存和递归栈空间均为 `O(n)`。

### 方案二：递推

递推把同一张状态表按从左到右填出。`f[i]` 仍表示以 `nums[i]` 结尾的最长长度；轮到 `i` 时，前面的 `f` 已有答案，直接枚举它们更新即可。与记忆化搜索的差别仅是控制流程：一个按需要递归，一个按顺序循环。

:::viz approach="community-iterative-dp"
:::

时间复杂度 `O(n^2)`，空间复杂度 `O(n)`。

### 方案三：贪心 + 二分（额外空间）

社区把同长度候选压缩成 `g`：`g[k]` 是长度 `k + 1` 的递增子序列能拥有的**最小末尾元素**。同长度的末尾 `99999` 和 `9`，后者严格更有用：任何能接在前者后的数也能接在后者后；大的末尾是被支配的数据。

`g` 升序排列。对每个 `x`，二分第一个 `>= x` 的位置；在末尾就扩展长度，否则用 `x` 替换，保留更小结尾。这是官方二分方案的同一核心，但从“删除无用状态”的角度建立不变量。

:::viz approach="community-greedy-binary-extra-space"
:::

时间 `O(n log n)`，额外空间 `O(n)`。

### 方案四：贪心 + 二分（原地修改）

该写法不单独创建 `g`，而把输入数组的前 `ng` 项当成 `g`。在 `nums[0:ng]` 内二分，把当前 `x` 写回定位位置；只有写到末尾时 `ng` 加一。播放器的高亮前缀就是当前 `g`，后面的内容不再承担候选结尾含义。

原题只需返回长度，因此可以复用输入空间；若题目要求输入保持不变，就不适用。

:::viz approach="community-greedy-binary-in-place"
:::

时间 `O(n log n)`，额外空间 `O(1)`。

### 方案五：返回一个具体的 LIS

原题只要求长度，前面的 `g` 无需保存路径。若要返回一条具体序列，则额外保存两类下标：每个 `g[k]` 所对应的原数组下标，以及每个元素应连接的前驱下标。二分位置为 `j` 时，当前元素的前驱就是长度 `j` 候选的末尾下标。

处理完后，从最长候选末尾沿 `previous` 不断回溯，再反转，便得到一条真实的 LIS。这里不把候选结尾数组误作答案，而用前驱链还原答案。

:::viz approach="community-reconstruct-lis"
:::

构建和回溯总时间 `O(n log n)`，额外空间 `O(n)`。

## 复杂度对比

- 官方方案一：动态规划 — `O(n^2)` 时间，`O(n)` 空间。
- 官方方案二：候选序列 + 线性扫描 — `O(n^2)` 时间，`O(n)` 空间。
- 官方方案三：候选序列 + 二分查找 — `O(n log n)` 时间，`O(n)` 空间。
- 社区方案一：记忆化搜索 — `O(n^2)` 时间，`O(n)` 空间。
- 社区方案二：递推 — `O(n^2)` 时间，`O(n)` 空间。
- 社区方案三：贪心 + 二分（额外空间）— `O(n log n)` 时间，`O(n)` 空间。
- 社区方案四：贪心 + 二分（原地修改）— `O(n log n)` 时间，`O(1)` 额外空间。
- 社区方案五：返回具体 LIS — `O(n log n)` 时间，`O(n)` 空间。
